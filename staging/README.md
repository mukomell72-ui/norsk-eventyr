# Серверное тестовое окружение Norsk Eventyr 9.1

## Локальные артефакты

- `node tools/build-staging-server.cjs /tmp/norsk-eventyr-staging` собирает HTML, ресурсы и 12 существующих Vercel Functions в `.vercel/output` указанного каталога. Каталог вывода должен быть пустым.
- `node tools/build-staging-sql.cjs > /tmp/norsk-eventyr-staging.sql` формирует транзакционный SQL для пустого тестового проекта Supabase. Команда только читает файлы. Роли `anon`, `authenticated`, `service_role` и схема `auth` предоставляются Supabase. Для SHA-256 требуется `pgcrypto` в схеме `extensions`.
- Корневой `vercel.json` по-прежнему описывает статический Preview с отключённым Git-деплоем и блокировкой `/api`. Серверный пакет использует собственный вывод Build Output API v3.

## Настройка после отдельного разрешения

1. Создать независимый чистый проект Supabase. Проверить его project ref и имя целевой базы перед применением сгенерированного SQL. Использовать только синтетические аккаунты. Источник структуры `norsk_eventyr_sync` — SQL `deferred/SECURITY_8_2_SYNC_PREPARE.sql` и тест `tests/sync-owner-sql-8.2.cjs`. Старые анонимные RPC в тестовой базе не создаются. Исторический DDL рабочей таблицы отсутствует в репозитории.
2. Создать отдельный Vercel-проект с именем `norsk-eventyr-staging`, включить Deployment Protection, задать переменные только для Preview, без подключения рабочего домена или Git-автодеплоя. Убедиться, что автоматически доступен `VERCEL_ENV=preview`. Для восстановления пароля сервер использует системный URL Preview этого проекта. В Supabase задать отдельный Site URL и разрешить только точный тестовый URL перенаправления.
3. В Preview задать `NE_SERVER_MODE=isolated-staging`, `NE_STAGING_SUPABASE_REF`, `NE_STAGING_SUPABASE_URL` и `NE_STAGING_SUPABASE_PUBLISHABLE_KEY` от нового проекта, отдельный случайный `NE_SESSION_SECRET` длиной от 32 символов и тестовое значение `NE_LEGAL_CONTROLLER_NAME`. Ключи с привилегиями `service_role` для приложения не требуются. Сверить принадлежность publishable key в панели Supabase, так как из формата ключа нельзя извлечь ref.
4. Проверить защищённый Preview с двумя синтетическими аккаунтами. Проверить согласие с условиями, облачную синхронизацию и конфликт ревизий, отсутствие доступа между аккаунтами, отсутствие запросов к рабочему хосту. Использовать короткие синтетические записи для проверки микрофона.
5. Перед платными проверками согласовать расходы и подтвердить доступность моделей, лимиты OpenAI и актуальные цены. Затем использовать только отдельный ключ тестового OpenAI-проекта в `NE_STAGING_OPENAI_API_KEY` и явно задать `NE_STAGING_AI_ENABLED=1`. Без обеих настроек вызовы провайдера блокируются. Ограничить доступ к ключу и отслеживать расход по проекту.

## Ограничения

Аудиозапись ограничена 2 900 000 байтами после декодирования. Размер JSON для аудиомаршрутов ограничен 4 000 000 байтами. Обычные JSON-запросы ограничены 128 КиБ, запросы синхронизации — 1 МиБ, содержимое состояния — 750 000 байт. Сохраняются существующие ограничения отдельных полей и маршрутов.

Атомарный лимит общей базы резервирует до 120 вызовов OpenAI за весь пилот, включая потенциальные повторы и проверки результата. Невыполненные резервы не возвращаются. Действуют и существующие ограничения на пользователя и маршрут. Лимит выражен в вызовах и не гарантирует стоимость в пределах 10 €. Провайдер и тарифы определяют фактическую стоимость. До разрешения на платные операции использование OpenAI остаётся выключенным.
