## Прямая read-only проверка действующего Supabase 10.10.2026
- `norsk_eventyr_sync` и `norsk_eventyr_ai_usage` существуют, `RLS=true`, anon/authenticated без прямого SELECT.
- `ne_sync_v2` и `ne_ai_quota_check`: SECURITY DEFINER, безопасный пустой search_path, доступны authenticated и недоступны anon. `ne_sync_v2` содержит проверку `auth.uid()` и владельца. Таблица sync имеет `owner_user_id` и индекс.
- Действующих облачных sync-записей при проверке **0** (из них ownerless **0**). Число может измениться; не считайте нулевые записи доказательством отсутствия локального прогресса.
- Все четыре старых `norsk_eventyr_sync_*` SECURITY DEFINER RPC пока доступны anon. Старые клиенты 8.0.1 используют bearer-secret схему. **Не отзывать преждевременно.**
- В Supabase Advisor остаётся предупреждение о выключенной leaked-password protection и предупреждения по SECURITY DEFINER EXECUTE. Не ставить permissive RLS политики.
- В Supabase нет изолированной ветки; создавать за счёт владельца только после проверки стоимости и явного согласия. По официальной документации branching compute платный и не покрывается Spend Cap.
- Приложение хранит локальный прогресс независимо от облака. Реальный экспорт/импорт и rollback должны быть проверены на разных аккаунтах.

## Vercel: существующая конфигурация на момент проверки
- `NE_SESSION_SECRET`, `OPENAI_API_KEY`, `NE_LEGAL_CONTROLLER_NAME` присутствуют для Production/Preview (значения не раскрыты); проверить актуальность при самом выпуске.
- Отдельные `NE_DISTRIBUTED_QUOTA=enforce` и `NE_SYNC_V2_ENFORCE=enforce` были настроены на СТАРУЮ feature-ветку; для текущего RC отдельной привязки нет. В Production код **сам** требует quota/v2 и должен возвращать безопасный 503 при недоступности RPC; в Preview эти пути нельзя считать протестированными.
- RC Preview может обращаться к живой Supabase; не переключать защищённые пути и не запускать тестовые миграции на живой базе.
- Firewall/WAF и реальные ограничения расходов/оповещения AI-провайдера **не подтверждены**. WAF-правила применяются к живому трафику — согласовать значения, сначала Log, затем блокировка; учесть shared-IP.
- Не считать лимит количества AI-вызовов реальным потолком расходов: модели, длительность аудио и токены стоят по-разному.

## Выпускная последовательность: строгие фазы
### Фаза A — подготовка, разрешена сейчас
1. Проверить весь список автоматических тестов на одном SHA, отсутствие регрессий, Preview READY, пробную Android сборку.
2. Пройти read-only аудит `deferred/RELEASE_8_2_READONLY_AUDIT.sql`; сохранить агрегаты, права функций и настройки. Никаких SQL, меняющих данные.
3. Определить контакт для privacy, фактические сроки хранения, законные основания, подрядчиков, страновые передачи, DPA, процесс выгрузки и **полного** удаления аккаунта (включая auth.users, отзывы, ошибки, устройства, историю доступа, облако и локальную копию).
4. Для коммерческих функций согласовать условия продления/стоимости/НДС/возвратов; для выпуска без оплат не включать ложные обещания или приём оплаты.
5. Утвердить целевую месячную сумму AI, лимиты/оповещения и WAF; не применять живые настройки во время подготовки.

### Фаза B — изолированная rehearsal, НЕ выполнена
1. После согласия на расход создать независимую Supabase ветку/клон с отдельными ключами. Не переносить реальные пользовательские данные в небезопасный тестовый контур.
2. Создать/подтвердить резервную копию продуктивных данных и **тестовое восстановление**; отдельно выгрузить локальный прогресс с Android и проверить импорт.
3. Сверить фактически установленный SQL с staged-скриптами; если функции уже существуют, проверить сигнатуры и поведение перед повторным применением. Не переустанавливать автоматически.
4. Подключить отдельный Vercel Preview к **тестовой** БД и включить строгие `NE_DISTRIBUTED_QUOTA` и `NE_SYNC_V2_ENFORCE` только в изолированной ветке; проверять JWT с двумя учётными записями и отменённым доступом.
5. Проверить ownerless→owner claim по правильному секрету; другой аккаунт, неверный секрет, конфликт ревизии, повтор отправки, таймаут, cloud delete и откат. Проверить квоты и ошибки 403/429/503.
6. Проверить login/reset, подтверждение почты, email/IP сценарии и два устройства; убедиться, что старые данные не теряются и что старые версии не работают вразрез с новыми.
7. Проверить возможность полностью удалить и экспортировать **все** персональные сведения; одного удаления cloud-copy недостаточно. `auth.users` каскадирует большинство привязанных строк, но ownerless legacy-cloud данные требуют отдельного учёта. Не использовать пользовательские данные в destructive тестах.

### Фаза C — gate до выпуска
GO разрешён только если:
- [ ] Завершена rehearsal с доказанным восстановлением и откатом;
- [ ] Проверены Production secrets, Auth, WAF и AI cost alerts;
- [ ] Подписаны/размещены достоверные Privacy/Terms, отработан account-delete/export процесс;
- [ ] Нет критичных Security Advisor проблем;
- [ ] Ручные Android+Web 2-user smoke и независимая языковая проверка ключевого B1–B2 материала сделаны;
- [ ] Повторный QA APK Vercel Preview совпадают с последним SHA;
- [ ] Отдельное однозначное разрешение владельца на **конкретный SHA** и Production window.

### Фаза D — будущая публикация (ТОЛЬКО ПО КОМАНДЕ)
1. Подтвердить backup/restore и снять агрегированный read-only снимок `sync`.
2. Без разрушения поддерживаемых клиентов установить/проверить аддитивные DB изменения; действующие v2 SQL уже имеются — повторное выполнение без анализа запрещено.
3. Под контролем переключить Production на проверенный SHA; сделать smoke Auth, AI, devices, cloud sync и отчёт об ошибках.
4. Старые анонимные RPC отключать отдельным разрешённым cutover **только после** перехода всех поддерживаемых клиентов на authenticated v2 и успешного теста. Ранее использовать `deferred/SECURITY_8_2_SYNC_CUTOVER.sql` нельзя.
5. Если проблема: остановить выдачу новых доступов, откатить web к предыдущему working deployment; после cutover откат одного web **недостаточен**, требуется совместимое, заранее испытанное состояние RPC. Не возвращать публичные legacy grants без отдельного решения и анализа риска.
