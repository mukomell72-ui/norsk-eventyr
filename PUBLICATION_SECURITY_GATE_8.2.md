# Norsk Eventyr 8.2 — выпускной контроль безопасности (9 октября 2026)

**Решение: NO-GO для публичной публикации. Допустимо только ограниченное тестирование на feature-ветке.**
Черновой PR #38, `feature/8.2.0-placement-calibration`. До отдельного письменного разрешения владельца нельзя сливать в `main`, деплоить Production, менять рабочую Supabase, активировать тарифы или выкладывать в Google Play.

## Выполненные улучшения кандидата
- Сессионная HMAC-подпись больше не использует известный всем запасной ключ `missing-secret`. Рекомендуемый параметр `NE_SESSION_SECRET` — отдельный длинный секрет на сервере; временно поддержан прежний `OPENAI_API_KEY` для совместимости. Не хранить значения в Git.
- Отдельно отклоняются `Sec-Fetch-Site: cross-site`, чужой Origin и небезопасная схема Origin для опубликованного HTTPS-хоста.
- Счётчики запросов ограничены по памяти, очищаются после истечения окна; ключ endpoint не зависит от query string. **Это по-прежнему не глобальное распределённое ограничение**, нельзя считать полноценной защитой AI-бюджета.
- Cloud proxy проверяет набор параметров, UUID, размер и структуру JSON, целочисленную ревизию; внутренние тексты ошибок PostgreSQL не передаются клиенту; установлен таймаут.
- Регрессионные тесты `tests/release-security-8.2.mjs` включены в обязательный GitHub QA. Фактические результаты и SHA нужно подтвердить по последнему успешному запуску после финального коммита.

## Критические выпускные барьеры

### 1. Cloud RPC: владельца данных должен проверять сервер и база — BLOCKER
Фактическая read-only инспекция Supabase (`rskgbkgtrigtznnksbyp`) обнаружила четыре вызываемые ролью `anon` функции `norsk_eventyr_sync_{create,pull,push,delete}`, все `SECURITY DEFINER`. Они защищены длинным синхронизационным секретом и SHA-256 хешем, но **не привязаны к `auth.uid()`** и доступны напрямую через Supabase REST, минуя Vercel API и отзыв доступа к аккаунту. RLS на таблице включена, но функция SECURITY DEFINER может её обходить.

До выпуска в изолированной тестовой базе:
1. Спроектировать новые привязанные к владельцу RPC (или хранилище с RLS и `auth.uid()`) с подлинным Bearer токеном зарегистрированного пользователя; токен проверять во всех операциях.
2. Ограничить `EXECUTE` у новых функций, закрепить безопасный `search_path`, запретить обход через старые анонимные RPC и прямой Data API. Проверить отсутствие непривязанных команд от анонимного пользователя.
3. Перенести существующие анонимные коды без потери прогресса через отдельное одноразовое подтверждение прежнего секрета в **авторизованном** аккаунте. Предусмотреть объединение разных устройств и отзыв доступа.
4. Отдельно протестировать два аккаунта/два устройства, чужие ID, повторное использование кода, конфликт ревизий, пропавшую сеть, отзыв доступа, удаление аккаунта и резервное восстановление.
5. Лишь после проверки и согласованного окна выпуска изменить продуктивные SQL/API одним согласованным планом. **Не отзывать старые RPC вслепую: это сломает действующую синхронизацию.**

### 2. Общий контроль AI-расходов и атак — BLOCKER
Лимитер `api/_guard.js` живёт в памяти одного Vercel Function процесса, поэтому не ограничивает запросы на всех экземплярах. Настроить в Vercel Firewall *WAF Rate Limiting* для чувствительных `/api/*` (генерация, чат, речь, восстановление доступа, облако); тестировать в режиме Log, затем применять 429 с измерениями ложных срабатываний. Для бюджетов нужны также лимит потребления **на авторизованного пользователя** и предупреждения/бюджетные пределы у AI-провайдера. Учитывать, что многие пользователи могут иметь общий IP.
Источник: https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting

### 3. Supabase Security Advisor — BLOCKER
Read-only проверка 2026-10-09:
- `auth_leaked_password_protection` — предупреждение, защита от утёкших паролей не включена;
- `anon_security_definer_function_executable` — 6 предупреждений, включая четыре cloud RPC и две явно публичные аналитические/отзывные функции;
- `authenticated_security_definer_function_executable` — 39 предупреждений, проверять каждую функцию на `auth.uid()` / owner проверку; нельзя автоматически считать все уязвимыми;
- 55 `rls_enabled_no_policy` — информационные сообщения, включая закрытые таблицы других продуктов в общей базе; **не** добавлять универсальные permissive policies.
До релиза включить подходящие Auth-меры и повторно проверить Security Advisor. Официальная справка: https://supabase.com/docs/guides/api/securing-your-api

### 4. Персональные данные и юридические условия — BLOCKER
Существующий экран условий предупреждает об AI-ошибках, но необходимо юридически проверить и до регистрации доступно опубликовать полную политику:
- идентичность и контактные данные ответственного за обработку, способ обращения и удаления учётной записи;
- основания/цели, категории email, устройств, учебных ответов, аудио, облачного прогресса, отзывов, логов;
- провайдеры обработки (Supabase, Vercel, AI), международная передача и сроки хранения;
- права пользователя и процедуры экспорта/удаления, резервные копии и инциденты;
- условия пробного срока, продления, цена/НДС, платные подписки/возвраты до начала коммерческих продаж.
Ключ `NE_LEGAL_CONTROLLER_NAME` и контакты сверить в развёрнутой среде без вывода секретов. Изменение версий `TERMS_VERSION`/`PRIVACY_VERSION` согласовать с серверным принятием условий; не делать молчаливый апдейт.
Официальная справка: https://www.datatilsynet.no/rettigheter-og-plikter/virksomhetenes-plikter/hvordan-lage-en-databehandleravtale/

### 5. Реальные тесты и образовательные заявления — BLOCKER
Нужны физический Android (разрешения микрофона, фактическая запись/ASR, звонок/переход в фон, отсутствие сети, login/reset, logout, прогресс, публичная оценка), независимые проверки преподавателя Bokmål B1/B2 и прозрачная маркировка предварительных AI-баллов. Нельзя рекламировать гарантированный CEFR B2 или официальный Norskprøven без реального доказательства.

### 6. Контроль выпуска, резервная копия, откат — BLOCKER
Перед релизом: один зафиксированный конечный SHA, успешно завершившиеся QA и APK, готовый Vercel Preview **того же SHA**, ручной smoke E2E, проверенные переменные среды и права, сверка лицензий аудио/изображений, изолированная DB-копия для миграционного rehearsal, проверяемые backup/restore и процедура отката web + миграций. Любая миграция сначала проверяется на копии. Разрешение владельца оформляется отдельным явным решением; до него `main` и Production не изменяются.
