# Norsk Eventyr 8.2 — процедура полного удаления аккаунта
**Черновик для владельца и ответственного за данные. Не выполнять удаление без подтверждённого запроса пользователя.**
Это инструкция по обслуживанию обращений; ни один этап пока не проверен как полный end-to-end процесс. Отдельную функцию самосервисного удаления аккаунта приложение не содержит.

## 1. Получение и верификация запроса
1. Опубликовать рабочий email `[УКАЗАТЬ КОНТАКТ]` в политике конфиденциальности, доступной ДО регистрации. Предусмотреть альтернативный способ обращения.
2. Принять запрос на доступ, экспорт, исправление или удаление; зарегистрировать дату, тип и срок ответа без избыточных персональных данных.
3. Установить, что запрос относится к **своему** аккаунту. Не отправлять данные и не удалять аккаунт только по совпадению введённого email. Использовать проверяемое подтверждение владения учётной записью или разумную эквивалентную проверку. Никогда не запрашивать пароль/BankID.
4. Объяснить последствия: прекращение доступа, удаление облачного прогресса; **локальный прогресс на телефоне пользователь удаляет самостоятельно**, поскольку у сервиса нет удалённого доступа к локальному хранилищу.
5. Отметить, какие сведения могут требовать сохранения по закону (например, реально созданные расчётные документы) и на какой срок. Не обещать немедленно уничтожить резервные копии, если это технически не так; сообщить фактический цикл перезаписи.

## 2. Проверка фактического состава данных (read-only)
На 10 октября 2026 в текущем Supabase проекте таблицы `norsk_eventyr_access`, `norsk_eventyr_access_grants`, `norsk_eventyr_ai_usage`, `norsk_eventyr_client_errors`, `norsk_eventyr_devices`, `norsk_eventyr_entitlements`, `norsk_eventyr_feedback`, `norsk_eventyr_installs`, `norsk_eventyr_lifecycle_events`, `norsk_eventyr_payments`, `norsk_eventyr_promo_redemptions`, `norsk_eventyr_subscriptions` имеют FK по `user_id` в `auth.users(id)` с `ON DELETE CASCADE`. Таблица `norsk_eventyr_sync` связана по **nullable** `owner_user_id` c ON DELETE CASCADE; старые записи без владельца могут остаться. Некоторые таблицы имеют `created_by`, `referred_by`, `moderated_by` с ON DELETE SET NULL.
- Проверить все новые таблицы и не связанные с FK хранилища/внешние логи, прежде чем считать процедуру полной.
- Данные об оплате, при наличии, требуют отдельной проверки юридического срока хранения и законности удаления.
- Не использовать email-совпадение как самостоятельное основание для удаления чужих ресурсов или связей.

## 3. Ручная обработка владельцем — ТОЛЬКО ПО ОТДЕЛЬНОМУ ЗАПРОСУ
1. Проверить подтверждение личности и при необходимости предоставить JSON-экспорт/выписку данных.
2. Снять доступ/активные сессии; убедиться, что новые записи в процессе удаления не создаются.
3. Согласовать удаление с юридическими требованиями и процессом ведения резервных копий.
4. Использовать проверенный Auth Admin workflow Supabase для конкретного подтверждённого `auth.users.id` (не создавать публичный endpoint с service-role key). **Выполняет исключительно владелец/оператор; этот файл ничего не удаляет.**
5. Проверить отсутствие строк пользователя во всех таблицах по `user_id`, затем по `owner_user_id`; проверить устройства, отзывы, аналитику, event logs и внешние сервисы. Отдельно рассмотреть старые ownerless-ссылки, идентифицированные достоверно и безопасно.
6. Зафиксировать ответ пользователю с выполненными действиями и обоснованными исключениями. Не раскрывать внутренние токены, ключи синхронизации, UUID третьих лиц или содержимое чужих данных.
7. Уточнить реальное время удаления из резервных копий и у субпроцессоров.

## 4. Выпускной тест на ИЗОЛИРОВАННОЙ тестовой базе
- Создать два искусственных пользователя, разные progress, устройства, события, отзывы, резервные копии.
- Смоделировать запрос удаления пользователя A; убедиться, что пользователь B и его данные остаются неизменными.
- Убедиться, что код старой синхронизации не позволяет заново создать/получить данные удалённого владельца.
- Отдельно проверить ownerless-legacy link; безопасное удаление/отзыв без раскрытия чужих данных.
- Проверить прекращение сессии, экспорт перед удалением, отсутствие повторной авторизации и срок обработки внешних логов.
- Проверить исключения (законные обязательства хранения), подтверждение исполнения и ошибочные запросы.
- Сверить настройку каскадов с фактической БД на момент выпуска.
